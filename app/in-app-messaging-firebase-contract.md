# In-App Messaging Firebase Contract

This document defines the API contract for messages handled by `InAppTripMessagingService.broadcastMessage(UUID userId, String message)` and the Firebase JSON payload generated from that flow.

## 1) HTTP Endpoint Contract (Inbound to Backend)

### Endpoint

- **Method:** `POST`
- **Path (as currently mapped):** `/messaging/postMessage`
- **Handler:** `MessagingController.postMessage(...)`

`MessagingController` now uses class-level `@RequestMapping("/messaging")`, so this endpoint is explicitly namespaced under `/messaging`.

### Headers

- `Authorization: Bearer <jwt>` (required)
- `Content-Type: application/json` (or `text/plain` when sending plain text)

### Request Body

Current implementation expects `@RequestBody String message`.

#### Accepted body form (recommended for JSON clients)

```json
"Carpool is leaving in 5 minutes"
```

#### Plain text form (also works)

```text
Carpool is leaving in 5 minutes
```

### Validation and Behavior

- JWT is verified via `TokenManagementService.verifyToken(authHeader)`.
- Sender user ID is extracted from the verified token.
- `broadcastMessage(userId, message)` loads all users in the sender's open trip.
- Sender does not receive their own message (`if (id.equals(userId)) continue`).
- For each recipient with a registered token, the service sends a Firebase data message.

### Success Response

```json
{
  "success": true,
  "message": "message posted",
  "data": null
}
```

### Error Responses (from shared/global handlers)

```json
{
  "success": false,
  "message": "<error message>",
  "data": null
}
```

Common cases include invalid/missing token, token verification failure, and Firebase send/runtime failures.

## 2) Firebase Message Contract (Outbound to FCM)

`broadcastMessage(...)` creates a `ChatMessageDto` and calls `FirebaseMessagingService.sendData(userId, chatMessageDto)`.

### Chat Payload Object (`ChatMessageDto`)

```json
{
  "timeStamp": "2026-08-01T14:20:11.182",
  "senderName": "Jane Doe",
  "message": "Carpool is leaving in 5 minutes"
}
```

Field definitions:

- `timeStamp` (`string`): ISO-8601 `LocalDateTime` generated by the server.
- `senderName` (`string`): display name of the sender resolved from the authenticated user ID.
- `message` (`string`): sender-provided chat text.

### FCM Envelope Sent by `sendData(...)`

```json
{
  "message": {
    "token": "<recipient_fcm_token>",
    "data": {
      "payload": "{\"timeStamp\":\"2026-08-01T14:20:11.182\",\"senderName\":\"Jane Doe\",\"message\":\"Carpool is leaving in 5 minutes\"}"
    }
  }
}
```

Notes:

- `data.payload` is a JSON-escaped string, not a nested JSON object.
- This `sendData(...)` path does **not** include `originService` or `notificationType` keys.
- If recipient token is missing/blank, message is skipped for that user.

## 3) Client Parsing Contract (Inbound to Mobile/Web Client)

When a client receives the FCM data message:

1. Read `message.data.payload`.
2. Parse/unescape it as JSON.
3. Deserialize into:

```json
{
  "timeStamp": "<ISO_8601_datetime>",
  "senderName": "<sender_display_name>",
  "message": "<chat_text>"
}
```

## 4) Backward Compatibility Guidance

- Keep `timeStamp` key spelling exactly as-is to avoid client regressions.
- Keep `senderName` in camelCase and treat it as required for updated clients.
- Keep `data.payload` as a string while existing clients depend on current parsing.
- If migrating to structured payloads, introduce versioning (for example `payloadVersion`) before changing shape.
